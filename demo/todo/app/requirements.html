Tsumiki — the 8 requirements

The whole spec of the task tracker, in the order a demo proves them.

derived a value the app computes from other state — the kind that drifts silently, and the reason a demo of this is worth watching. Five of these eight are derived.

R1

Adding a task puts it in the list

Typing a task and pressing Add (or Enter) shows it as a new row, unchecked, at the bottom — exactly the text typed. An empty input adds nothing; the Add button is disabled.

proof: the new row is read off the visible list, and its added just now stamp is present.
R2

A task can be edited in place, and the change is stamped

Double-clicking a task title (or the edit icon) makes it editable; Enter saves the new text in the row, Escape cancels. Saving a real change records an edited time.

proof: rename a task on screen, read the new title back off the row, and confirm the meta line flipped from added to edited just now.
R3

A task with sub-tasks is a container with a progress ringderived

Sub-tasks live inside a task. A task that has them shows a progress ring counting them (2 of 3) instead of its own checkbox — you can’t tick a container by hand, only its sub-tasks.

proof: add a sub-task on screen and the ring must move 2/3 → 2/4 by itself, with no checkbox on the parent to click.
R4

Completion rolls up, both directionsderived

Completing the last open sub-task completes the container by itself; reopening any sub-task reopens the container. The explicit “Complete all / Reopen all” action flips every sub-task at once — nothing is ever toggled by a stray click on the parent.

proof: tick the last sub-task and read the parent row’s done-state off the screen; then reopen one sub-task and watch the parent reopen. The dojostack inheritance story, in kindergarten words.
R5

“To do” counts remaining leaves onlyderived

The header count is the real amount of work left: open sub-tasks, plus open tasks that have no sub-tasks. A container is scaffolding — it never counts as a unit of work itself.

proof: complete one sub-task → the count drops by exactly one. “Complete all” on a container of two open subs → it drops by exactly two, not three. The subtlest rule here, and the one the red demo breaks.
R6

Smart views filter correctly, and the sidebar counts agreederived

All shows everything; Active hides done tasks; Today shows only not-done tasks due on or before today; Completed shows only done tasks. Each view’s sidebar badge equals the number of rows it actually shows.

proof: for each view, count the visible rows and compare with the sidebar badge — on screen, not in code.
R7

Due dates derive an overdue / today chipderived

A not-done task due before today wears the red “overdue” chip; due today wears “today”; a future date shows the date; done tasks wear no date chip.

proof: deterministic via the ?now= frozen clock, so the golden run pins the calendar and the same chips appear every run.
R8

Everything survives a reload

Tasks, sub-tasks, done-states, titles, due dates, order, and every created / edited / completed timestamp all come back after the page reloads.

proof: reload the real page mid-flow and read the same structure — and the same done · edited stamps — off the fresh screen.

R2, R3, R4, R5, R6, R7 read values the app computes. R1 and R8 bookend them. One flow proves all eight.
