C1 · checkReq cannot say which beat it proves any time

The situation. A requirement's PRD has a behavior block of numbered beats (Given, then When→Then 1, When→Then 2, …). A test tags the requirement with checkReq('R5', fn) — but the tag names only the requirement; which beat a given assertion is proving is inferred from the run's structure. In six places across the suite that inference cannot be made honestly, so those beats carry a declared intent gap — the visible debt npm run proof lint prints on every run, by design never a pass and never silently attributed to the wrong beat (rule 3).

The proposal. An optional second argument: checkReq('R5', { beat: 2 }, fn). Existing tests change nothing (the argument is optional); the six ambiguous sites name their beat explicitly and the gaps close. The lint gains one guard: a named beat that does not exist in the PRD's behavior block is refused, so a stale number is an error, never a wrong picture.

Recommend: yes. Small, additive, honest — it converts six permanent "we cannot say" rows into six attributed proofs. Folded into phase 5 (it touches spec/_base.ts and the lint, nothing in storage).
What could go wrong if you say yes: beat numbers become one more thing an author must keep aligned with the PRD. If you renumber a behavior block and forget the test, the lint catches a beat that no longer exists — but a beat that still exists with a different meaning (you swapped beats 2 and 3) would be misattributed until the Changed-drift or a human eye catches it. The mitigation is the existing reqhash drift: editing the PRD flips the requirement to Changed/unproven anyway, forcing a re-look.

C2 · Evidence keyed by requirement vs by test must be ruled before T7

The situation. Harvested evidence (the frames, skeletons, replicas of each beat) is filed under the requirement — one deterministic slot per reqId.beat. Coverage is many-to-many by design: a flow on the init screen can legitimately prove board:R1. On 2026-09-04 that combination bit us (the I5 incident): the init flow, run alone, rewrote board/evidence/R1.b1.* with pictures photographed on the init page, pruned what the board's own run had put there, and the next board run went red on four tests. The standing patch is a precedence rule: the home screen's own test owns its beats, a flow may only fill beats left empty, and the reporter marks a flow's version foreign without copying its bytes.

today — keyed by requirement

board/test.spec.ts run → writes ↘

board · R1.b1 — ONE slot

init flow (tags board:R1), run alone → writes ↗ the SAME slot

Two writers, one address. The precedence rule referees forever; the flow's fresher photograph of that beat is deliberately thrown away because the stale home picture holds the slot.

proposed — keyed by test

board/test.spec.ts → board/test · R1.b1

init flow → init/flow · R1.b1

Two writers, two addresses — a collision is structurally impossible; the precedence rule, the foreign marker and the discard all get deleted. R1's reader lists evidence from every test that covers it, each under its own name.

Why now: T7 rewrites the reporter's landing path and T3 builds the one-time importer. Re-keying during that rewrite is one shape decision; re-keying after it is a second migration of the same data. That is the whole reason this needs your ruling before implementation starts.

Recommend: key by test. It removes a whole class of bug plus the workaround that referees it, and provenance gets cleaner — a picture always says which test took it.
What could go wrong if you say yes: (1) the reader needs one new display rule — when two tests prove the same requirement, whose pictures headline the beat row? (proposed: the home screen's own test headlines; other tests listed beneath, one tap away — your eye on the first mock decides). (2) Storage grows slightly: two covering tests each keep their beats instead of sharing one slot — bounded by the same gc, and honest, since they photographed different pages. (3) The index shape changes, so T3's importer carries the mapping — done once, inside the task that exists anyway.

The one live residue: this repo's own git history. Years of committed harvests grew claude-plugin-spec's .git to ~850 MB. T11 stops the growth (nothing derived is tracked from then on) — but the 850 MB of history stays in every full clone until the history itself is rewritten. A rewrite (filter-repo dropping the old evidence paths) shrinks clones to a few MB, at a real price: every commit sha changes. Your other Claude sessions' checkouts, the marketplace install, any fork or open PR — all must re-clone; anything pinned to an old sha breaks.

Recommend: defer. Do it — if ever — right after 0.45.0 ships, in a quiet moment you pick, with every session's work committed and pushed first. Until then, a heavy clone is a one-time cost per machine (and git clone --depth 1 avoids it entirely); a botched or badly-timed rewrite costs every clone at once.
What deferring costs: every full clone keeps downloading 850 MB of dead pictures, and the marketplace copy stays heavy. If new-machine setup pain matters to you sooner, say so and it becomes a scheduled task with a coordination checklist instead of a someday.
