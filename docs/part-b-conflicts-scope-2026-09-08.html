Part B — the Conflicts page

Part A shipped (five buckets, stamps, slots, question cards; the board and demo/todo both dogfood it, 37/37 green). Part B is the other half of the method: when two sources state one fact incompatibly, it is a conflict, not a gap — and the Conflicts page is where a human picks the canonical side. This scopes the four changes that turn today's page into that.

The page already exists — its R1–R5 are step 3 of the flow (a conflict is one fact stated two ways; both positions shown with provenance; you pick canon; resolving dispatches the rewrite; decisions survive a rescan). Part B extends it; it replaces nothing.

MOCKWhat a finding becomes

Today a finding has two sides, a and b, each a quote. Part B makes sides a list, each carrying a kind — where the claim came from — and, where it can, a picture instead of a quote.

How many sides? Two is the floor, there is no ceiling

A side is an item in a list, not one of a fixed a/b pair — so the count follows the disagreement, not a template.

Two sources

The floor. The same grid renders two columns side by side — spec-vs-code, code-vs-actual, whichever two disagree. No special case, no empty third slot.

Many sources — e.g. three docs disagree

Each doc that states the fact differently is its own doc side, carrying that doc's path as its source — plus any spec/code/actual side. Still one finding (one fact), N sides. The row wraps or scrolls, so six sides read as cleanly as two; the picture sides share the one stepper.

One thing to keep straight: a finding is one fact stated incompatibly. Three docs describing three different facts are three findings, not three sides of one. Three docs giving three answers to the same question (how wide is the canvas?) are three sides of one finding. The scan (change 2) groups by the fact, so this is a scan-time call — and, like everything it writes, "leave it out if unsure".

The three play modes — inherited, for free

A picture side is Part A's reader: the base with a claim applied, on the same stepper. So auto · semi-auto · step carry over with zero new code — the mode picker drives every picture side and the Actual recording together, exactly as it drives the Focus reader today. A single-moment claim (a width, a count) has one still, so the modes are moot there; a claim that spans several moments plays through them under whichever mode is set. Nothing new is designed here — reusing the stepper is the whole point of doing A before B.

6.1–6.4The four changes, in order

1
Sides carry a kind. A finding's sides become a list of { kind:'spec'|'doc'|'code'|'actual', source, date?, quote, claim?:{locator,expected} }. Two sides is the floor. Existing a/b findings migrate as two spec sides; settled keys are content-keyed already (R5) and survive untouched. Pure, unit-tested migration.
2
The scan is bounded per screen. Its comparison surface is exactly the screen's prd, the docs the prd's grounding notes cite, and the code files they cite — nothing wider. Still a claude job, still "leave it out if unsure", still stamped as authored (never a measured green).
3
A side can be a picture. Where a side carries a claim and the screen has a harvested base replica, the card renders that side as the base with the claim applied — one Expected column per side, the Actual recording beside them, on the reader's one stepper with its three play modes. This is why Part A's Expected-view work is the prerequisite: Part B reuses graft · stand · the srcdoc sheet as-is. It also retires the parked hand-drawn compare-player mock; only its row shape survives.
4
Resolve follows the loser's kind. spec → the existing rewrite dispatch. doc → recorded as a note for the doc's owner, no rewrite outside the board. code → recorded; the rule card reads mismatch until a red-first test and a fix land. actual → never rewritten (a written side winning over the actual makes the row red; the actual winning makes the written side lose).

One dependency, already met. Part B's picture side needs a screen's harvested base replica + a claim — both of which Part A's Expected view already ships (the reader composes exactly this today). So B needs A, and A is done. Nothing in B needs a new capture or a new render primitive.

ORDERRecommendation

Build in the numbered order — 1 (kinds + migration) is the spine everything hangs off, and it's pure and safe. 2–3 are additive (a wider scan, a richer render) and can't regress Part A. 4 (resolve-by-kind) touches the one existing behaviour (the rewrite dispatch), so it lands last with the conflicts-screen tests around it.

Rough size: change 1 is an afternoon (pure + tests). 3 is the largest but is mostly wiring the existing graft into the conflicts render. 2 and 4 are small. Call it a focused day or two, most of it low-risk because the render primitive already exists.
