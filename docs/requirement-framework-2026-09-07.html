The requirement framework — rules, examples, questions

2026-09-07 · a proposal on the human's re-thought flow ("user found a page super hard to debug") · references found online, not invented · worked on the todolist demo's real doc, code and spec · nothing here is built yet

A feature is a set of rules. A rule is proven by examples (its Given / When → Then beats). Whatever the sources cannot settle is a question — and the questions, sorted conflict → orphan → mismatch, are exactly the list the human has to confirm.

  1. Layer 1 · GROUP = the five buckets ruled canon yesterday (lifecycle · derived numbers · views & chips · survival · mistake path). Fixed rows, in fixed order, on every screen — an empty bucket is a visible hole, the way Example Mapping reads a rule with no examples.
  2. Layer 2 · RULE = a requirement card, one promise. It carries a source stamp: what the DOC says, what the CODE does, what the SPEC (prd) says, and whether a test PROVES it. The stamps are the capture (step 2.1) made visible.
  3. Layer 3 · EXAMPLES = the beats, filed into four slots: happy (the promise kept), boundary (the empty, the max, the no-change), absence (what must not appear — our rule 2 said out loud), mistake (the slip is safe). A rule is fully understood only when every slot the rule needs is filled or explicitly marked "not needed". A yellow slot is a gap, not a red.
  4. The four states, in the order the human works them — this is what "what needs confirming" means:
agreed every source says the same, a test proves it — nothing to confirm
conflict two sources disagree — pick a side (step 3)
orphan / gap one source only, or a slot empty — is it a requirement?
mismatch agreed rule, actual differs — bug, or wrong rule? (step 4; step 5 when words fail)
Why conflict comes before orphan. An orphan behaviour is only a question once the rule around it is settled: "the code hard-deletes" is a question about delete until the human says whether delete must be reversible — then it is a mismatch. Ordering the states this way is what turns a capture into a queue the human can walk top to bottom.

What the todolist teaches. Seven of nine rules are agreed, yet the page still carries 14 things the human has never been asked — two conflicts, four behaviours the code has that no document owns, seven promises three sources make that no film shows. None of them is on the board today, because the board only knows a requirement once someone wrote a ## R. The framework's whole value is that the capture writes the questions down in the bucket they belong to, so the human confirms one bucket at a time instead of re-reading the code.

4How to group it — three ways, the failure mode first

A · By bucket, states inside recommended · five fixed rows, cards sorted conflict → orphan → gap → agreed within each
① The task's life — R1 · R2 · 3 orphans② Derived numbers — R3 conflict · R4 · R5③ Views & chips — R6 · R7④ Survival — R8⑤ Mistake path — R9 conflict
It is the canon walk of 2026-09-06 with the questions filed where they belong. An empty bucket is a hole the human can see; a bucket with three orphans says the doc is thin there.
Failure mode: bucket names are the author's vocabulary. A user arriving with a symptom ("the ring is wrong") may not know it lives in ②. Mitigation: the counter on top lists mismatches and conflicts by name and links into their bucket — the symptom finds its row without the user knowing the taxonomy.
B · By journey Patton's backbone: add → organise → complete → review → keep
Add — R1 · due date · EnterOrganise — R2 · sub-tasks · fold · R3Complete — R4 · R5 · bulkReview — R6 · R7Keep — R8
Reads like the app; a stakeholder recognises every row. Feature Mapping is built on it.
Failure mode: a journey has no slot for survival or the mistake path — R8 is bolted on as "keep", and R9 has nowhere to live at all: delete is not a stage of the journey, so the demo's one red row and its conflict vanish into "Organise". The buckets exist precisely because a journey hides what is missing.
C · By decision kind three queues: conflicts · orphans/gaps · mismatches
Conflicts (2) — R3 number · R9 deleteOrphans / gaps (11) — due date · fold · delSub · Enter · Escape · …Mismatches (1) — R9
The shortest path to "what do I have to decide" — a pure to-do list.
Failure mode: it strips context. R9 appears in two queues; the delete orphan (delSub) and the delete conflict never sit together; the human reassembles the rule in their head. Kept as the counter, never as the grouping.
Recommendation: A, with C as the counter on top. The buckets are already the human's ruling, they are the only grouping that makes an absent requirement visible, and sorting by state inside each bucket gives the human the queue without losing the rule around it. When a bucket grows past ~5 cards (a dojostack calculation screen will put twenty in ②), the author-named families of today (### n · family) become sub-groups inside a bucket, not a rival grouping.

Statesproven / unproven / failed / changed, derivedthe same four stay derived; conflict and orphan / gap are new, also derived — from the stamps and the slots, never stored
What this is not. Not a new status field (there is none, and this adds none: every state above is derived from stamps and slots). Not a gate (a question card blocks nothing; the board keeps folding). Not non-functional coverage — performance and accessibility stay out, as they are today.

6The one thing to settle first

Should the five buckets become the fixed grouping on every screen, replacing free-form families? Everything else above follows from the answer: the question cards need a bucket to live in, the empty-bucket signal needs fixed rows, and the counter needs a place to link into. My recommendation is yes, with today's families demoted to optional sub-groups inside a bucket. If no, approach A collapses into B-with-badges and the "what is missing" signal is lost.

Answer that and the next step is the written spec (docs/superpowers/specs/…) and a plan — the capture of doc + code into candidate cards first, on the todolist, before any board rendering.
