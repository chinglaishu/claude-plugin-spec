It is not the SVG. It is the skeleton and the house style. A real HTML replica can be almost the same.

Your question was whether the schematic looks unlike the component because it is SVG, and whether it could be a real HTML component instead. Below is the House View version picker three ways, from real data: the current drawing, the photograph, and an HTML replica captured from the live app's DOM in one pass.

SVG can render anything pixel-faithfully if it is given the data. The unlikeness comes from two steps before the format: the drawing is derived from a skeleton that keeps at most 360 boxes with one kind, one text, one colour, a font size and an alignment each, and the renderer then paints that skeleton in house style, snapping colours to six dye tokens and drawing containers as hairlines and buttons as wash plates. That house-style decoupling was a deliberate choice on 2026-08-18. Given your priority, it is the choice to reverse.

The replica uses the app's font stack (Geist, then system-ui). On a machine without Geist it falls back, which is the one fidelity limit that needs a decision: embed the app's web fonts once per screen, or accept the fallback.

What changes, in order

  1. Capture. Beside each skeleton, proveVisible also serialises the scene root around the ring (the ringed element's region, bounded by node and byte caps) into evidence/<id>.b<k>.<phase>.dom.html: computed styles diffed against defaults into classes, inline svg kept, images and web fonts fetched once per screen as data URIs, scripts and handlers stripped. A self-contained module beside _layout-walk.mjs, unit-tested the same way.
  2. Intent, at capture time. The claim is known the instant the frame is taken, so the intended replica is produced in the page by mutating the clone: the leaf that reads got takes expected; a missing element is restored from the beat's last right replica; a never-there one gets a marked placeholder. Both replicas are stored; the fold needs no DOM library.
  3. Board. The schematic cell renders the intended replica in a sandboxed srcdoc iframe scaled to the cell, stepped per moment exactly as the SVG stills are today, with the difference marker and the loupe from the previous review. The house-style drawing stays only for a screen with no UI.
  4. Gate. Right after capture, the replica is rendered in a hidden iframe on the same page and walked with the existing skeleton walk; boxes and words must match the live skeleton within tolerance, or the harvest records a replica gap and proof mirror refuses it. Likeness verified by measurement, not by eye.
  5. Archetypes. Unchanged for the no-UI case; later, sketch inside a sibling screen's real replica so even the pre-UI picture wears the product.

About two weeks of staff work end to end, most of it in the capture and the sanitiser. What it reverses is one design decision, the house-style decoupled drawing of 2026-08-18; that reversal is yours to make, and this page is the recommendation to make it.
