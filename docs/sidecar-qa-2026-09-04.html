2026-09-04 · answers to the three questions after moving dojostack's board out of dojostack_main

Superseded the same evening: the human chose to keep the board inside the app repo as specboard/ — the whole folder gitignored by the app, local-only, single user, not a git repo of its own (the human declined that; team sharing is the coming cloud step) — and made that the rule for every project (specboard 0.44.0-e). Section 1 below describes the intermediate sibling layout; sections 2 and 3 stand unchanged (the nested folder is the same thing, one level in).

2 · A product with no main repo (frontend repo + backend repo)

The sidecar already is this case: the board never needed a main repo, only a running app URL (spec/_config.json baseUrl — tests drive the app over HTTP, not through files). Two small additions make it clean:

myapp-frontend/.specboard → ../myapp_specboard
myapp-backend/.specboard → ../myapp_specboard
pointer, one line each
myapp_specboard/spec/ · tools · board.html · its own gitmanifest app: { frontend: "../myapp-frontend", backend: "../myapp-backend" }
baseUrl, over HTTP
the running appdev server · preview URL · staging
  • Pointer in every repo an agent works in. kg-staff / kg-deep run from either repo and land on the same board.
  • app becomes a map when there is more than one repo (a string stays valid). Only project helpers read it — a seed script that shells into the backend, governs: paths qualified by key (backend:src/api/x.py), the capabilities scan of each repo's .claude/. The fold itself never reads app code.
  • CI: the e2e gate runs in the board repo against a preview URL; the app repos trigger it with repository_dispatch carrying that URL. This is the one piece of choreography the layout costs.
Recommendation: make the sidecar the default for every project and the vendored-in layout the exception. One model, one place for the harvest, and the app repo never carries anything but one line. Failure mode I argued against: a fresh clone of an app repo shows no board until the sidecar is cloned too — the pointer names it, and kg-init can clone it, so discoverability survives.

Recommendation, staged: (1) now — Git LFS on *.png *.woff2 *.webm in the sidecar, no code; (2) next — route evidence through the existing storage config to a bucket and let the board read bucketUrl paths; (3) then — publish the sidecar's board.html + index as a static site so the team reads the board without a server. A hosted multi-tenant "specboard cloud" is step 4 and only worth it once step 3 is used by more than one project.
Failure modes to hold in mind: evidence shows real customer data, so any bucket must be private and the hosted board behind auth; GitHub LFS is 1 GB free then metered, and dojostack already grows ~20 MB per harvest; tools/evidence.mjs relies on deterministic paths that overwrite in place — a content-addressed store changes that contract and the fold's prune must be re-proven; a read-only hosted board loses Run/Scan/Compose, which is fine only if runs move to CI first.
