3 · Both paths are one pipeline; the switch is where the fold lands

The two paths share the folder layout, the harvest, the fold and the gates. The cloud path adds exactly one verb, publish, and one reader. That is why they should be one config value, not two products: a project starts local and flips to cloud without moving a file.

4 · How the cloud path could be built — three options

A · git-only: LFS for blobs, index committed
Failure mode: GitHub LFS is 1 GB free then metered; dojostack grows ~20 MB per harvest, so a team burns the quota in weeks. The index still churns every commit. Readers need a checkout and a local server. Two harvesters on one branch conflict on binary paths.
  • zero code, works today
  • proof is versioned with the code
  • does not give a teammate a URL
B · private blob store + static hosted board (recommended)
Failure mode: screenshots show real customer data, so the store must be private and the board behind auth from day one. Content-addressed blobs break the "deterministic path overwrites in place" contract that tools/evidence.mjs prunes by, so the fold's prune must be re-proven in the store. Two teammates harvesting the same screen need a merge rule: the index is folded per screen, last run wins per screen, never a whole-index replace.
  • storage config already has where: bucket and shipToBucket
  • board.html is already static: publish it + the index, reads blobs by URL
  • one bucket per project (S3 / R2 / GCS), the user's own; no specboard account
  • CI can be the harvester: proof follows every merge
C · specboard cloud service (multi-tenant)
Failure mode: accounts, billing, tenancy and an API before a second team has used B. The product becomes a service to run, not a plugin to install, and the customer's screenshots now sit on your infrastructure.
  • the best onboarding: paste a token, done
  • only worth it once B is used by more than one project
  • B's store layout is what this would serve, so B is not thrown away

5 · "Does it make a difference to store in the codebase or the cloud?"

Yes, and the answer differs by tier. Authored files must be in the codebase: they change with the code, they are reviewed with the code, and a test that is not in the repo cannot run in the repo's CI. Derived files must not be in the codebase: every harvest makes them a new permanent blob. Whether the derived files sit on a disk or in a store is the only local-versus-cloud question, and it is answered by who needs to read them.

The fold index is the one that looks like it could go either way. It should not be committed: it is measured, not authored, and the board already refuses to trust it when the sources moved. In the cloud it gets the thing committing it was trying to buy, "proof at commit X", without the churn.

7 · Decisions for you

D1 · Authored files in the app repo. Reverse the "gitignore the whole specboard/ folder" rule: commit prd.md, test.spec.ts, steps.ts and _specboard.json; ignore evidence/, _runs/, _results-index.json, board.html, viz/, _fonts/. You ruled the opposite on 2026-09-04; this is the case for changing it, because a product cannot keep its users' requirements on one disk. Recommend: yes.
D2 · The cloud path is B (the user's own private store + a static hosted board), with C only after a second team uses it. Recommend: B.
D3 · Tools run from the plugin, version-pinned per project, instead of vendored into each project. Recommend: yes, as a separate step after D1 and D2 — it changes kg-init and kg-update, not the storage.

Order if all three are yes: D1 (a .gitignore and the scaffold, one day) → the plugin repo stops committing its harvest and CI publishes (path B's first user, this repo) → the publish verb and the store contract for any project → the hosted read-only board → D3.

Why .git is 850 MB, and how to stop it

causesizemechanism
evidence frames committed and rewritten~890 MB of blobs, 11,537 objects87 harvest commits; deterministic paths overwrite in place, so one frame (R1.b1.after.png) has 54 versions in history, each a full PNG — git cannot delta binaries usefully
board.html committed177 MB206 commits of an 8 MB generated file
deleted but remembered~130 MBdemo/todo evidence 84 MB · viz sketches 25 MB · the v1 knowledge-graph 24 MB — deleting a file never shrinks history
loose, unpacked objects298 MB6,659 objects git has not packed yet; git gc compacts them (safe, no history change). The real history is the 552 MB pack.

Prevention, in order of effect: (1) never commit a derived file — the .gitignore in section 2; (2) the plugin ships a guard: npm run proof (or a pre-commit hook kg-init installs) refuses a commit that stages evidence/, board.html or the index; (3) the dogfood board and demo show their pictures from a CI artifact or a hosted static page, never from a commit; (4) once, rewrite this repo's history with git filter-repo to drop those paths — the pack falls to tens of MB. That step rewrites every commit sha and needs a force push and a fresh clone for the other session, so it is your call and a coordinated one.

10 · Self-hosted platforms as a reference — Langfuse and its neighbours (asked 2026-09-05)

None of them keeps records in the user's code repo. Each splits its data into metadata (small, queried, in a database) and blobs (large, written once, in an artifact or object store), and the local install differs from the cloud only in which backend each store points at.

platformself-hosted locally, where the records goformatwhat to borrow
Langfuse (v3)Docker Compose on the user's machine: Postgres for projects, users, prompts, datasets; ClickHouse for traces, observations, scores (the high-volume half); Redis as the ingestion queue; an S3-compatible blob store (MinIO in the default compose) for raw event batches, media attachments and exports. Everything lives in Docker volumes; the app repo holds only the SDK call.relational rows + columnar rows + objects by keythe four-way split is what a multi-user product needs; it is far more than a single user's board needs. Langfuse v2 was Postgres-only and was replaced because trace volume outgrew one database — the lesson is "blobs out of the database from day one".
MLflowlocal default: metadata as files under ./mlruns (or SQLite), artifacts in a directory; server mode: --backend-store-uri (Postgres) + --default-artifact-root (S3/GCS)files or SQLite + a directory of artifactsthe closest to specboard: two knobs, metadata store and artifact store, each with a local-directory default and a remote option. Our index is the metadata store, evidence/ is the artifact store.
Arize Phoenixphoenix serve writes one SQLite file in a working directory; Postgres is optional for teamsSQLitea single-file database is the honest step between "JSON on disk" and "a server", if the index ever needs querying across runs

Grafana · GiteaSQLite by default, Postgres/MySQL when configured; uploads on local diskSQLite + filessingle-binary tools default to one file and a directory; they do not ask a solo user to run a database

What this means for specboard's local path: keep the index as a file and the evidence as a directory. A database earns its place only when there are several writers or cross-project queries, and SQLite would be the first step then, not Postgres. The cloud path is MLflow's second knob: the artifact store becomes a bucket and the index a per-commit object, with the same fold in front of both. Langfuse's stack is what path C (a hosted multi-tenant service) would look like, and it is why C comes last.
