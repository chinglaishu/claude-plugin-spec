specboard storage — claude-mem × Langfuse, plus the local/cloud media switch

2026-09-05 · a step-back design on the human's two references and one new requirement: media (images/video) stored locally but out of the repo, or as a cloud blob URL — the user's choice. This supersedes the location half of the earlier re-rule; the SQLite half stands.

Langfuse adds the hosting shape: the app you run locally is a real server owning a real store (DB + object storage), writers write through one interface, and "cloud" is configuration on the same stack, never a fork of it. specboard keeps exactly that: the board server owns the store; going shared later means the same server on a shared host with Postgres behind the same interface.

2 · The design in one picture

app repo (git)

Authored only: prd.md, tests, rulings, the manifest with projectId + the media choice.

Zero derived bytes — not even ignored ones except the vendored tools and per-machine config.

→

the board server (local host) → the db (switch 1)

The fold, runs and every blob reference are rows behind ONE async store interface, two drivers: sqlite — ~/.specboard/<projectId>/board.db, the default — or pg — a remote database URL the whole team shares.

The reporter writes through store.mjs; the board reads and serves. One door.

→

the blob store (switch 2)

fs: ~/.specboard/<id>/blobs/<sha256>.<ext>, served at /blob/…

s3: the same sha256-named object PUT to an S3-compatible bucket (S3, R2, B2, MinIO); the db stores its URL.

Team enablement is exactly two values (the human's rule, 2026-09-05): a remote db url + a cloud blob url. Set both and every teammate's ordinary local board — and CI — reads and writes the same record and the same media. No hosted board is required for a team; hosting one read-only later is an optional extra for people who don't run the tool.

The one trick that makes the switch cheap: a db row's picture reference is a single column with two shapes — blob/<sha>.png (the local board serves it) or https://… (the browser fetches it straight from the bucket). The client already treats a src as opaque; nothing in the board cares which it got. Content-addressing survives the switch: the object's key IS the sha256 either way, so dedupe (an unchanged frame costs nothing) and gc-by-reference (delete what no record names — fs unlink or s3 delete) are the same logic behind a two-method driver: put(bytes, ext) → src, remove(src).

3 · The switch, and where each piece of config lives

media: "local" — the default

Blobs land in ~/.specboard/<id>/blobs/. Out of the repo by location. Zero setup, works offline.

Sharing: your board is yours; teammates run their own; CI's artifact is the shared record.

media: "cloud" — a URL per blob

Blobs PUT to the configured bucket; the db keeps the URL. The board (and anyone the URL reaches) renders straight from it.

Sharing: this is the stepping stone — proof media is already team-visible before any hosted board exists.

committed · spec/_specboard.json — the project's shared policy (modes + non-secret endpoints; a team agrees once) "projectId": "tsumiki-3f9a1c", "db": "local" | "remote", — switch 1: board.db, or the team's database "media": "local" | "cloud", — switch 2: blobs/ on disk, or the bucket "bucket": { "endpoint": "https://…r2.cloudflarestorage.com", "name": "specboard-tsumiki", "publicBase": "https://media.example.com" } — cloud only; no secrets here per machine, never committed · env (or spec/_config.json) SPECBOARD_DB_URL — the remote db url (postgres://…; carries its password, so env-only) SPECBOARD_S3_KEY / SPECBOARD_S3_SECRET — the bucket credentials — only ever here machine-global · ~/.specboard/settings.json — claude-mem style: defaults (retention N, ports), overridable per project

A run with media: "cloud" and no credentials fails the fold loudly (rule 3 — never a silent local fallback that quietly forks the store). The video and 1280px frames are ~95% of the bytes, so the switch governs the whole blob store — patches, skeletons and fonts ride along, keeping one path instead of two.

4 · The team path becomes three gentle steps, not one cliff

  1. Solo, today: local db + local blobs.

    Everything under ~/.specboard/. The claude-mem experience: install, run, it just works, the repo stays pure.

  2. Flip media: "cloud" when proof should be showable.

    Same board, same local db, but every photograph and video is a URL a teammate (or a PR comment, or a ticket) can open.

  3. Flip db: "remote" when the team should share one record.

    Two values total — the remote db url and the bucket — and every teammate's local board, plus CI, reads and writes the same fold and the same run history. Test records land in the shared db from wherever the suite runs. This is the Langfuse move — configuration, not a rewrite.

  4. Optional, later: host a read-only board

    for people who never run the tool — the same server pointed at the same two values, on a shared box.

Shared-db semantics, stated plainly: run records are append-only (every teammate's run is kept, with who/when); the per-screen fold is latest-wins, so the current truth is whoever ran that screen last — with CI's run on every push as the steady arbiter; gc's keep-set is computed from the shared db itself, so one teammate's cleanup can never delete what another's retained run still names.

6 · Trade-offs, stated before you agree

Cloud mode's honest costs: credentials to manage (env-only, never committed — and the fold fails loudly without them); the board needs the network to show old proof; a public publicBase means anyone with a URL sees that screenshot (fine for most teams, wrong for regulated ones — signed URLs are the escape, more moving parts); gc must be trusted to delete from a bucket (mitigated by the lifecycle-rule backstop).
Home-dir mode's honest cost: two checkouts of the same project share one store (same projectId) — usually a feature, but two simultaneous harvests from two checkouts must not interleave (already the standing never-run-concurrent-harvests rule; the db adds real transactions, which makes this safer than the file fold, not worse).
Recommendation: build it exactly as drawn — home-dir store (claude-mem), board-server ownership with SQLite (Langfuse), one blob driver with the fs/s3 switch in the committed manifest, defaulting to local. It adds one small interface to T1 and one manifest field to T4; everything else in the plan stands.
