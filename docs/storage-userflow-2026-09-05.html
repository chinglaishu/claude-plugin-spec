The purpose, in one line. A feature whose requirement has gone messy — every fix on the page triggers the next bug — and the plugin lets a person and the agent agree on what the feature should do by picture, then hold the app to that picture. Two gaps, in order: what the agent thinks versus what the person means, and what the picture shows versus what the app does.

Two rules fall straight out of the flow. The agent works inside the repo, so the requirement must be there for it to read — that is what breaks the "prompts live in the platform's database" analogy from Langfuse: their consumer is a running app, ours is a coding agent sitting in the checkout. And the harvest is read by two readers, the person and the agent, so the data home must stay plain files an agent can open, whatever else it becomes for a team.

4 · What this changes in the storage plan

A · fold as a file + blobs by hash now; a database at the team step recommended Steps 2–4 read the latest state and nothing else; step 5's CI reads a verdict. Nothing in the flow queries across runs on one laptop. A database earns its place when a team shares a board and wants history per commit — and there it is Postgres beside the bucket, the cloud step, not SQLite on a laptop.
  • MLflow's local default, exactly
  • no native dependency to install for a solo user
  • the agent keeps reading plain JSON + files
  • last N run indexes kept as files answers "what did it look like 3 runs ago"
Failure mode: when the team step comes, the fold is imported into Postgres once — a migration we write then, against a schema this file already mirrors.
B · SQLite now, Postgres later (this morning's answer) The same split, with the fold in a per-project SQLite file from day one.
  • one query layer for local and cloud
  • history per run from the start
Failure mode: better-sqlite3 is a native module every plugin user installs, and the reporter, spec-store, server and builder are rewritten before a single user has reached step 5. The flow does not ask for it.
C · keep the harvest in the repo What this repo and demo/todo do today.
  • a picture in every PR, zero infrastructure
Failure mode: 850 MB of history here already; every plugin user clones it. The harvest lives until the next run — git keeps it forever.
Unchanged from this morning: authored files in the app repo (the folder's whole-tree ignore is reversed, the vendored code stays ignored inside it); the harvest in ~/.specboard/<project>/, content-addressed, GC'd to the last N; the cloud is one switch on the same fold; the git-branch shipper goes.
Changed: the database moves from "now, SQLite" to "the team step, Postgres". The sketch (viz) is no longer a stored file at all. CI at step 5 needs nothing beyond the test in the repo and a verdict — the frames are a CI artifact with a retention, and the team store is opt-in.

5 · One decision

D · Take A: the local fold stays a file and a blob directory, and the database arrives with the team store. Recommend: yes. If yes, the order is: (1) the data home + blob store + GC and the importer of today's harvest, pure and unit-tested; (2) the reporter, spec-store, server and builder read and write it, and this repo + demo/todo stop tracking their harvest; (3) scaffold, update and the skills flip the folder to committed-authored-only, and dojostack migrates; (4) the CI file for step 5; (5) the team store when a team asks.
