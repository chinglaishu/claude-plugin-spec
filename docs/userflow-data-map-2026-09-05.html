1 · First, the five places a file can live

Every file in this document lands in exactly one of these. The whole design is one sentence: git keeps only what a person or an agent wrote; everything a test run produces lives in a per-project directory under your home folder, and reaches git nowhere.

Committed — specboard/ in the app repo

The authored text: requirements, tests, the human's rulings, the manifest. Kilobytes. Lives as long as the feature does. This is what your coding agent and CI read from the checkout.

Ignored — also in specboard/, kept out of git

The vendored plugin code (~45 MB) and per-machine scratch like ports and a sign-in script. All of it regenerable; the folder's own .gitignore keeps it out.

The data home — ~/.specboard/<project-id>/

Everything a run produces: the fold, the run records, and every photograph, skeleton and replica — each stored once under the hash of its own bytes (blobs/<sha256>.<ext>). 10–50 MB per screen, latest run wins, never in any git.

CI artifact / team store — copies that leave the machine

CI zips its runner's data home and keeps it 14 days for reviewers. Later, when a team asks, the same files go to a bucket + database instead — not in this plan.

Never stored — the drift itself

Proven / unproven / Changed is computed on every build by comparing the current requirement text against what the last run pinned. There is no status field anywhere, so there is nothing to go stale or to lie.

1b · Why is anything ignored at all — and how does a teammate get everything?

Because every ignored file is one of three kinds, and none of them is the thing a teammate actually needs:

ignored filewhy it stays out of githow a teammate gets theirs
tools/ · node_modules/ · board.htmlVendored / generated. ~45 MB of machinery that kg-update replaces wholesale — committing it means merge conflicts on every update and a bloated app repo.The committed manifest (spec/_specboard.json) names the exact release; kg-update + npm install re-vendor it identically on their machine.
spec/_config.jsonPer-machine, possibly secret. Ports and app URL differ per machine, and a sign-in script can carry a credential — a credential must never be committed.They write their own once. It is a few lines.
the harvest (in ~/.specboard/) · test-results/ · crawl.* · screen.pngDerived and churning. Every run rewrites it, only the latest proves anything, and git keeps every version forever — this repo grew to 850 MB of dead harvest history exactly this way.They run the suite once: the committed tests against the app regenerate the whole harvest on their machine. It is a cache of proof, not the truth — the truth is the requirements and tests, which they already cloned.

So a teammate's first hour looks like this:

  1. Clone the app repo.

    They now have everything anyone authored: every requirement, every test, every ruling, the manifest. That is the entire shared truth — a few hundred KB.

  2. kg-update + npm install.

    The manifest names the release; the same tools land in their specboard/, byte-identical to yours.

  3. Run the suite once.

    Their own ~/.specboard/<id>/ fills with a fresh harvest — their proof that the app on their machine meets the committed requirements. Sharing your harvest would only share yesterday's photographs of your machine.

  4. Want to see a run without running? Two paths.

    Today: CI runs the same suite on every push and keeps its harvest 14 days — download it, SPECBOARD_HOME=<dir> npm run board, and you see exactly what CI saw. Later: the team store — the same blobs to a shared bucket, the fold in a database, a hosted read-only board everyone opens. Deliberately deferred until a team asks (your ruling, 2026-09-05: local-first now, cloud when a team needs it).

The mental model: git shares the recipe (requirements + tests); every machine cooks its own meal (the harvest); CI is the shared kitchen whose meal anyone can inspect; the team store, when it comes, is the shared table. Committing the meal is the anti-pattern the 850 MB history proved.

The requirements themselves: for each one, a Given / When → Then. Canon the moment it is written — you edit or delete it exactly like text you wrote yourself. Retired (ruled by the human, 2026-09-05): there used to be a sketch here — a small drawn SVG cartoon of the requirement, shown only while it had never been harvested. Drafting a PRD therefore creates exactly one file.

4 · One test run, in order

Step 4 zoomed in: what actually happens between "the test starts" and "the board shows the fresh proof". Colour = where that step writes.

  1. Playwright runs the committed test.

    checkReq photographs the page around every assertion — before, each claimed value with its ring painted, after — and captures each moment's layout skeleton and Expected replica in the same instant.

  2. The raw attachments land in test-results/.

    Transient and ignored — the reporter reads them once, then they're trash.

  3. The reporter stores every attachment as a blob.

    Frames, skeletons, patch replicas, fonts, the video — each written to blobs/ under the sha256 of its own bytes. Anything unchanged since last run already exists and costs nothing. T7

  4. The beat's starting page becomes the shared base.

    The before replica, header stripped, stored once — a second beat starting from the same page hashes to the same blob, so one screen state is one file no matter how many beats use it. A3′

  5. The fold: this screen's entry is written into index.json.

    Verdicts, coverage, claims, the source fingerprints, and every blob name — folded in beside the other screens, never replacing them. T5

  6. The run record lands and old ones are pruned.

    runs.json plus runs/<id>/ (log, shots, video); only the last N are kept.

  7. The garbage collector sweeps.

    It computes the set of blobs the index and the kept runs still name; everything else under blobs/ is deleted. This is the entire retention policy. T2

  8. board.html is regenerated from the fresh index.json, and the server hands out exactly four kinds of thing: the board page, the authored spec/**, /blob/<sha>, and /runs/<id>/ — nothing else. T8

What you (and the agent) then read back, per moment: the Expected cell is the base blob with the moment's patch grafted on; the Actual cell is the ringed frame; a failed claim shows its expected and got, and the skeleton beside it is what the agent fixes the app from. All of it lives until that screen's next run — only the latest proves anything.

And if you edit the PRD afterwards (back to step 3): nothing is written — the edited text's fingerprint stops matching the fold's, and the requirement reads Changed / unproven on the next build.

5 · The one rule the whole map encodes

A file goes in git only if a person or an agent wrote it — the requirement, the test, your rulings, the manifest. Everything a run produces is stored by its content in the data home, kept exactly as long as something names it, and copied out only as a CI artifact or, later, to a team store. Nothing derived is committed anywhere, ever.

Sizes come from the measurements in storage-paths-2026-09-05.html (850 MB of harvest history in this repo before the change, 99 MB on dojostack, 10–50 MB per screen); per-file sizes are typical, not limits.
