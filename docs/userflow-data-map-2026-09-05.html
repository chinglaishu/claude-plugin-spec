1 · The grid — steps across, homes down, files in the cells

Two readings fall straight out of the grid. Everything a person or an agent writes stays in the top row — it is small, it is the requirement, and both the coding agent in the checkout and CI need it exactly there. Everything a run derives lands in the third row — big, regenerable, latest-wins — and reaches git nowhere, not in the app repo and not on a branch (the git shipper goes with T16). The two rows in between and below are the folder's own scratch and the copies of the third row that leave the machine.

The one rule the grid encodes. A file goes in git only if a person or an agent needs it in the checkout — the requirement, the test, the human's rulings, the manifest. Everything a run produces is addressed by its content in the data home, kept while something names it, and copied out only as a CI artifact or, later, to a team store. Nothing derived is committed anywhere.

Sizes are the measurements in storage-paths-2026-09-05.html (850 MB of history here, 99 MB on dojostack, 10–50 MB per screen) and the flow page; per-file sizes are typical, not limits. Step numbering follows the flow page; step 0 is the install the flow page leaves implicit.
