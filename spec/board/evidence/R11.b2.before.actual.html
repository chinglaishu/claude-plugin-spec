How specboard works

Every screen in a project is one row with two ends — requirements↔the tests that prove them. There is no status field anywhere: a requirement reads proven only while a passing test tags it with an assertion that would fail without it. Edit a requirement and its proof goes stale; delete an assertion and the green honestly disappears. The board never stores state — it derives it, on every build.

The CI gate is yours to choose — spec/_ci.json names the screens whose whole test.spec.ts runs in the GitHub Actions gate, and every home card in it wears a CI mark. Right now it names 4 screens: board · conflicts · init · _modes. Edit the list as screens are added, retired, or judged too slow to gate a merge; one left out still runs with npm run e2e.

the journey

Get the map once — then make each screen deep, one at a time

1 · Get the map — once
kg-init. The board lands in the repo, and the crawl inventories every screen it can reach. Nothing is faked.
kg-inittools/ + spec/

Scaffold the board

The board is vendored into the repo and serves on its own port. Your screens will be its rows.

a real browser, no drafting
kg-initcrawl.png · rows

Inventory the app

Each route is visited and screenshotted, and lands as a row with no PRD — visibly uncovered. The board now shows honestly what is not yet governed.

2 · Make each screen deep — one at a time
kg-deep, per screen, most important first. This is where requirements and proof actually come from.
kg-deepstudy · golden.json

Study the real screen, seed golden data

Source, testids, existing tests, contracts — then a deterministic fixture, so tests can assert exact numbers, not that boxes exist.

kg-deepprd.md

Draft the requirements

One requirement per behaviour, grounded in what the screen really does — canon the moment it is written, edited freely like any other requirement.

checkReq tags carry coverage
kg-deeptest.spec.ts

Prove with unit and flow tests

Unit tests prove the screen's own behaviours; flow tests cross screens along a chosen path — exact golden values, safe round trips, a writer flow that restores its own baseline. The board derives every requirement's state from the tags.

↻ then, before & after every change — forever
kg-staffbefore any edit

Run the change discipline

Find what governs the screen, learn the three times to stop and ask the human, and change things in the right order.

kg-updateon each release

Stay current

Bring the vendored board to a new specboard release — untouched files updated, your edits kept, conflicts dropped beside them to merge.
